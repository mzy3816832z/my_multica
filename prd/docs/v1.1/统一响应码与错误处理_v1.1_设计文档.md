# 统一响应码与错误处理 v1.1 系统设计文档

## 1. 概述

### 1.1 需求背景

架构审查（YUZ-201）发现当前系统接口错误处理存在不合理设计：业务错误与 HTTP 状态码混用。

- 业务异常 `BusinessException` 在抛出时同时把业务码放入 body（如 `code: 400002`）、把 HTTP 状态码置为 400/404/410，导致前端 axios 拦截器将业务错误误判为"接口调用失败"，无法按业务码做差异化处理。
- 业务码与 HTTP 码强耦合（400001→400、404001→404、410001→410），业务码未起到独立分层作用。
- 典型问题案例：
  - 登录密码错误：body `code: 400002`，HTTP `400 Bad Request` —— 被当成接口调用错误。
  - 用户不存在：body `code: 404001`，HTTP 404 —— 业务结果与"接口路径不存在"语义混淆。
  - 房源已下架：body `code: 410001`，HTTP 410 —— 前端无任何 410 处理逻辑，"已下架"引导页不会生效，形成断头路。

### 1.2 设计目标

1. HTTP 状态码只表达"接口调用层面"的结果，业务结果一律通过 body 内业务码表达。
2. 业务码与 HTTP 码解耦，按模块分段，可独立扩展。
3. 前端拦截器逻辑简化，业务错误可分发到页面级差异化处理。
4. 不破坏现有接口 URL 与成功响应结构，无数据库变更。

### 1.3 版本说明

本文档为 V1.1 迭代的设计补充（缺陷修复与架构优化类），不改变 V1.1 PRD（`prd/docs/iterations/v1.1/产品优化PRD-V1.1.md`）的业务功能范围。关联 Issue：YUZ-201 系统架构审查。

## 3. 详细设计

### 3.1 M1 后端统一响应与异常处理改造

#### 3.1.1 HTTP 状态码使用规范

| HTTP 状态码 | 语义 | 场景 |
|---|---|---|
| 200 | 请求被正常受理并返回 | 成功（`code: 0`）+ 所有业务校验不通过（`code != 0`） |
| 400 | 请求报文本身不合法 | JSON 解析失败、参数类型/格式错误（DRF `ValidationError`） |
| 401 | 未认证 / Token 失效 | `AuthenticationFailed`、`NotAuthenticated` |
| 403 | 已认证但无权限 | `PermissionDenied`（角色权限不足） |
| 429 | 触发频控 | `Throttled`、短信频控 `TooManyRequestsException` |
| 500 | 服务器内部错误 | 未捕获异常 |

**关键变更**：`BusinessException.status_code` 由 400 改为 200；`custom_exception_handler` 中 `BusinessException` 分支返回 `status_code=200`。`ParamErrorException` 保持 400（属报文不合法）；`UnauthorizedException` 保持 401、`ForbiddenException` 保持 403、`TooManyRequestsException` 保持 429（均属调用层问题）。

`NotFoundException`、`GoneException`、`ConflictException` 属于业务结果，HTTP 状态统一改为 200，语义由 body 业务码表达。

#### 3.1.2 业务码分层规范

业务码为 6 位数字，与 HTTP 码解耦，按模块分段：

| 段位 | 含义 | 示例 |
|---|---|---|
| 0 | 成功 | `SUCCESS = 0` |
| 400xxx | 参数/通用业务 | `PARAM_ERROR = 400001`、`BUSINESS_ERROR = 400002` |
| 401xxx | 认证类业务 | `UNAUTHORIZED = 401001`（Token 失效）、新增 `AUTH_FAILED = 401002`（用户名或密码错误）、`SMS_CODE_ERROR = 401003`（验证码错误或已过期） |
| 403xxx | 权限/账号状态类业务 | `FORBIDDEN = 403001`、新增 `ACCOUNT_DISABLED = 403002`（账号已被禁用） |
| 404xxx | 资源不存在类业务 | `NOT_FOUND = 404001` |
| 409xxx | 冲突类业务 | `CONFLICT = 409001`（手机号已注册、重复操作） |
| 410xxx | 资源状态类业务 | `GONE = 410001`（已下架/已删除） |
| 429xxx | 频控类 | `TOO_MANY_REQUESTS = 429001` |
| 500xxx | 服务内部错误 | `SERVER_ERROR = 500001` |

**具体修正项**：

1. `apps/users/views.py:135` 登录"用户名或密码错误"由 `404001` 改为 `401002`；同接口"用户不存在"（`User.DoesNotExist` 分支）与"密码错误"必须返回**同一个** `401002`，避免账号枚举。
2. 验证码错误（多处 `code=400002`）统一为 `401003`；账号禁用（多处 `code=403001`）统一为 `403002`。
3. 消除全部魔法数字：`apps/users/views.py` 中 13 处 `code=400002`/`409001`/`404001` 字面量全部改用 `ErrorCode` 常量；新增业务码必须先登记到 `core/response.py` 的 `ErrorCode` 与 `ERROR_MESSAGES`。
4. 参数校验失败统一 `400001`：修复 `apps/apartments/views.py:252`、`apps/audits/views.py:250` 等处将 serializer 参数错误误用 `BUSINESS_ERROR(400002)` 的问题；`apps/favorites/views.py:57` 已正确使用 `PARAM_ERROR`，作为范式。
5. `ParamErrorException(serializer.errors)` 目前把 errors 字典字符串化，前端无法展示。统一在 `custom_exception_handler` 的 `ValidationError` 分支（或 `ParamErrorException` 构造中）做"提取首条错误信息"，各视图不再各自实现 `_extract_first_error`。

#### 3.1.3 异常处理分支顺序

`custom_exception_handler` 中将 `BusinessException` 分支提前到 `ValidationError` 等分支之前（或改为显式类型映射表），消除新增异常子类时的匹配顺序隐患。

#### 3.1.4 已下架房源（410 Gone）闭环

采用方案 A：详情接口对已下架/已删除房源返回 HTTP 200 + `code: 410001`，`data` 中可携带 `apartment_id` 等最小信息；前端按业务码渲染"已下架"占位页（见 M2）。

### 3.2 M2 前端请求层与错误分发适配

#### 3.2.1 `web/src/utils/request.ts` 改造

- 成功回调中 `res.code !== 0` 分支：按业务码分发。`401001` 登出跳登录；`410001` 不弹通用 toast，reject 时携带 code 供页面级处理；其余业务码统一 toast `res.message` 并 reject（reject 的 Error 对象上挂 `code`，供页面 catch 后差异化处理）。
- error 分支只保留 HTTP 层处理：401 登出跳登录、403 权限提示、429 频控提示、5xx/网络异常提示。删除 `code === 401001` 等"HTTP 与业务码双判断"冗余逻辑。

#### 3.2.2 房源详情页 410001 占位页

`web/src/views/apartment/ApartmentDetailView.vue`：`getApartmentDetail` catch 到 `code === 410001` 时渲染"房源已下架"占位页（提示可去收藏列表取消收藏），替代当前仅弹通用 toast 的行为。

### 3.3 M3 文档与测试对齐

1. **Swagger**：所有接口 `@extend_schema` 补充错误响应声明（统一结构 `{code, message, data}`），200 响应中注明业务码可能性；drf-spectacular 可定义统一的错误响应 serializer 复用。
2. **后端测试**：业务错误断言统一为 `resp.status_code == 200` + `data['code'] == <业务码>`（`apps/users/tests.py` 现有断言已是此风格，以其为准对齐其余测试）；调用层错误断言 HTTP 状态码（401/403/429）保持不变；新增登录"用户不存在与密码错误同码"的断言。

## 4. 接口汇总

本次改造不新增、不删除接口，仅变更错误响应的 HTTP 状态码与业务码取值。统一响应结构不变：

```json
{ "code": 0, "message": "success", "data": {} }
```

变更前后对照（典型接口）：

| 场景 | 变更前 | 变更后 |
|---|---|---|
| 登录密码错误 | HTTP 400, code 400002 | HTTP 200, code 401002 |
| 登录用户不存在 | HTTP 400, code 404001 | HTTP 200, code 401002（与密码错误同码） |
| 验证码错误 | HTTP 400, code 400002 | HTTP 200, code 401003 |
| 账号被禁用 | HTTP 400, code 403001 | HTTP 200, code 403002 |
| 手机号已注册 | HTTP 400, code 409001 | HTTP 200, code 409001 |
| 房源已下架 | HTTP 410, code 410001 | HTTP 200, code 410001 |
| 参数校验失败 | HTTP 400, code 400001 | HTTP 400, code 400001（不变） |
| 未登录/Token 失效 | HTTP 401, code 401001 | HTTP 401, code 401001（不变） |
| 无权限 | HTTP 403, code 403001 | HTTP 403, code 403001（不变） |
| 短信频控 | HTTP 429, code 429001 | HTTP 429, code 429001（不变） |

## 5. 数据模型

无数据库变更。`ErrorCode` 常量类新增 `AUTH_FAILED = 401002`、`SMS_CODE_ERROR = 401003`、`ACCOUNT_DISABLED = 403002` 三个常量及对应 `ERROR_MESSAGES` 文案。

## 6. 非功能性设计

- **兼容性**：接口 URL、成功响应结构不变；仅错误场景 HTTP 状态码变化，前端同步改造后无兼容风险。第三方调用方（如有）需在发版说明中告知。
- **安全**：登录接口"用户不存在"与"密码错误"同码同文案，消除账号枚举风险。
- **可维护性**：业务码常量集中登记、禁止魔法数字写入编码规范；异常分支改为显式映射，降低后续扩展出错概率。
- **可测试性**：业务错误断言风格统一（HTTP 200 + body code），测试意图与实现行为对齐。
