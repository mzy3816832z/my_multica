# 房源上下架与变更审核机制 V1.2 系统设计文档

## 1. 概述

### 1.1 需求背景

V1.0/V1.1 已跑通「商家发布 → 平台审核 → 租客浏览/收藏 → 站内信通知」闭环，但业主实测反馈三个硬伤：
- 已上架房源只能删除、无法下架（删除为软删除且不可恢复）
- 审核中房源无法撤回编辑
- 变更审核触发仅覆盖 `name/district_id/street_id/detail_address` 四字段，价格/图片/面积/户型/设施/电话等均免审直改，真实性/合规红线失控

### 1.2 设计目标

基于《房源上下架与变更审核机制 PRD V1.2 定稿》实现：
- 状态机新增 `offline`（已下架）、`change_reviewing`（变更审核中，影子发布）两态
- 新增下架 / 重新上架 / 撤回三类商家操作
- 变更审核触发矩阵从 4 字段扩展为 A 类必审字段集，其余免审即时生效
- 影子发布：变更审核期间对外展示旧版，通过后新版本生效

### 1.3 版本说明

本次为 V1.1 → V1.2 迭代，在现有 Django DRF + Vue3 技术栈基础上增量开发。
- 向后兼容：新增状态不破坏既有 published/审核流程
- 决策记录（业主已确认）：D1 价格类免审；D2 变更审核期间展示旧版；D3 下架后重新上架免审
- PRD：`prd_房源上下架与变更审核_v1.2定稿.md`（附件）
- 关联 Issue：YUZ-195

## 3. 详细设计

### 3.1 M1 状态机扩展

**功能描述**：`Apartment.STATUS_CHOICES` 新增 `offline`、`change_reviewing` 两态。

**数据模型变更**：
- `Apartment.STATUS_CHOICES` 追加：
  - `('offline', '已下架')`
  - `('change_reviewing', '变更审核中')`
- `status` 字段为 CharField + choices，新增枚举无需 DB migration（值域扩展即可）。

**状态流转表**（商家可发起）：

| 当前状态 | 操作 | 目标状态 | 说明 |
|---|---|---|---|
| published | 下架 | offline | 立即隐藏 |
| published | 编辑（免审字段） | published | 即时生效 |
| published | 编辑（A类字段） | change_reviewing | 生成变更审核单，对外展示旧版 |
| offline | 编辑（A类字段） | offline | 生成变更审核单，保持 offline |
| offline | 重新上架（无 pending 审核） | published | 免审 |
| offline | 重新上架（有 pending 审核） | offline | 阻断，等待审核完成 |
| change_reviewing | 撤回变更 | published | 作废变更单，旧版继续 |
| pending_first_review | 撤回 | draft | 回草稿可编辑重提 |
| first_rejected | 编辑重提 | pending_first_review | 重新提交首次审核 |
| 任意未删除 | 删除 | 软删除 | 保留现有逻辑 |

**新增工具函数**（建议放 `apps/apartments/utils.py`）：
- `PUBLIC_VISIBLE_STATUSES = ('published', 'change_reviewing')`：对外可见状态集合
- `can_transition(current, action) -> target`：状态流转校验（或直接在各接口内联实现）

---

### 3.2 M2 下架/重新上架/撤回接口

**功能描述**：新增三个商家操作接口。

**接口定义**：

| 方法 | 路径 | 说明 | 状态流转 |
|---|---|---|---|
| POST | /api/v1/merchant/apartments/{id}/offline | 下架 | published → offline |
| POST | /api/v1/merchant/apartments/{id}/online | 重新上架 | offline → published |
| POST | /api/v1/merchant/apartments/{id}/withdraw | 撤回 | 见下 |

**下架（offline）逻辑**：
- 校验公寓属于当前商家；仅 `published` 状态可下架
- 置 `status='offline'`，返回成功

**重新上架（online）逻辑**：
- 校验公寓属于当前商家；仅 `offline` 状态可上架
- 若存在 `pending` 的 first_review 或 change_review 审核单 → 拒绝，返回错误「有变更待审核，请等待审核完成」
- 否则 `status='published'`（免审）

**撤回（withdraw）逻辑**（区分首次/变更）：
- `pending_first_review` → 置 `draft`，作废（软删除）关联 pending 首次审核单
- `change_reviewing` → 置 `published`，作废关联 pending 变更审核单（旧版继续展示）
- 其他状态 → 拒绝，返回错误「当前状态不可撤回」

**序列化器与路由**：
- 新增响应序列化器（含 `apartment_id`、`status`）
- `merchant_urls.py` 新增 3 个 path 绑定

### 3.3 M3 变更审核触发矩阵重构

**功能描述**：将编辑接口的 `KEY_FIELDS`（4 字段）扩展为 A 类必审字段集，其余免审即时生效；A 类变更置 `change_reviewing`（影子发布）。

**触发矩阵（定稿）**：

**A 类 — 必审（改「房源长什么样、在哪」）**：

| 字段 | 模型 |
|---|---|
| name | Apartment.name |
| district_id / street_id / detail_address | Apartment |
| longitude / latitude | Apartment |
| cover_image | Apartment.cover_image |
| room_types[].images | RoomType.images |
| room_types[].layout_type | RoomType.layout_type |
| room_types[].window_type（当前模型语义=内外窗） | RoomType.window_type |
| room_types[].area | RoomType.area |

**免审 — 即时生效（改「价格与补充说明」）**：

| 字段 | 模型 |
|---|---|
| rental_plans[].monthly_rent / lease_term / payment_method | RentalPlan |
| description | Apartment |
| contact_phone | Apartment |
| property_fee / water_fee / electric_fee / service_fee / other_fees | Apartment |
| room_types[].facilities | RoomType |
| room_types[].floor / sort | RoomType |
| room_types[].available_date | RoomType |

**说明与补充**：
- 字段分级通过 `system_dict`（category=`audit_sensitive_fields`）配置，运营可调。seed 脚本按上表写入 A 类字段 code。
- 判定粒度：逐字段比对，若请求数据中任一 A 类字段与现值不同（含房型数组内 A 类字段），判定「需审核」。
- `room_types[].name`（房型名称）PRD 未明确归类，默认按免审处理（展示性字段）。
- 注：PRD §5 将 `window_type` 标注为「朝向」，但当前模型 `window_type` 语义为「内外窗」（朝向字段已在 YUZ-233 移除），按模型实际字段纳入 A 类。

**影子发布逻辑（编辑 A 类字段时）**：
1. 校验公寓无未决（pending）变更审核单，存在则拒绝「已有变更待审核」
2. 构建 `original_data`（旧快照）+ `submitted_data`（新快照）+ `changed_fields`
3. 创建 `change_review` 审核单（pending）
4. 公寓 `status` 置 `change_reviewing`（而非原来的保持 published）
5. 返回 `{apartment_id, audit_id, updated: false}`

**免审逻辑（编辑仅免审字段时）**：
- 直接更新公寓/房型/租金方案，`status` 保持原状态（published 或 offline）
- 返回 `{apartment_id, audit_id: null, updated: true}`

**编辑 offline 状态房源**：
- 免审字段 → 直接更新，保持 offline
- A 类字段 → 生成 change_review 审核单，保持 offline（对外本就不展示，无需影子发布）

### 3.4 M4 影子发布过滤与审核回写

**功能描述**：对外查询过滤改为含 `change_reviewing`（展示旧版），审核通过/驳回适配 `change_reviewing` 回写。

**对外过滤变更**（所有公开房源查询）：

| 接口 | 现状过滤 | 变更后 |
|---|---|---|
| GET /api/v1/apartments（列表） | `status='published'` | `status IN ('published','change_reviewing')` |
| GET /api/v1/apartments/{id}（详情） | 校验 `status=='published'` | 校验 `status IN ('published','change_reviewing')` |
| GET /api/v1/apartments/{id}/room-types | `status='published'` | `status IN (...)` |
| GET /api/v1/room-types/{id} | `apartment.status=='published'` | `status IN (...)` |
| GET /api/v1/apartments/compare | `status='published'` | `status IN (...)` |
| GET /api/v1/apartments/{id}/nearby | `status='published'` | `status IN (...)` |

- 建议抽取公共常量 `PUBLIC_VISIBLE_STATUSES` 或复用 `Q(status__in=...)`，避免六处硬编码。

**审核回写适配（audits/views.py）**：

| 操作 | 现状 | 变更后 |
|---|---|---|
| approve（change_review） | 应用 submitted_data，未改 status | 应用 submitted_data + `status='published'` |
| approve（first_review） | `status='published'` | 不变 |
| reject（change_review） | 保持 published（当前无 change_reviewing） | `status='published'`（从 change_reviewing 恢复，旧版继续） |
| reject（first_review） | `status='first_rejected'` | 不变 |

**商家列表 status 筛选（merchant_apartment_list）**：
- `GET /api/v1/merchant/apartments` 新增 query 参数 `status`（可选），支持 `published` / `change_reviewing` / `offline` 等筛选
- 前端「已下架」tab 通过 `status=offline` 拉取

## 5. 数据模型

### 5.1 表变更

| 表 | 变更 | 说明 |
|---|---|---|
| apartments | STATUS_CHOICES 追加 offline/change_reviewing | CharField choices 扩展，无 DB 迁移 |
| system_dicts | 新增 category=`audit_sensitive_fields` | A 类字段 code 列表，运营可调 |

### 5.2 核心实体关系（不变）

- Apartment 1—N RoomType 1—N RentalPlan（不变）
- Apartment 1—N AuditRecord（变更审核单复用现有模型，submitted_data/original_data/changed_fields 语义不变）
- 新增状态仅作用于 `apartments.status`，不改表结构

### 5.3 数据流转（影子发布）

```
商家编辑A类字段
  → 生成 change_review 单（submitted_data=新版, original_data=旧版）
  → apartment.status = change_reviewing
  → 对外列表/详情仍读旧数据（库内旧值未变）
  → 管理员 approve：_apply_submitted_data 覆盖旧值 + status=published
  → 管理员 reject：保留旧值 + status=published（审核单 rejected）
  → 商家 withdraw：保留旧值 + status=published（审核单软删除）
```

## 6. 非功能性设计

### 6.1 一致性
- 所有「对外可见状态」判断统一走 `PUBLIC_VISIBLE_STATUSES = ('published','change_reviewing')` 常量，避免多处硬编码漂移
- 变更审核的「旧版展示」依赖库内旧值不变，编辑时不得先改库（A 类字段变更只写审核单快照，不落库）

### 6.2 并发与约束
- 同一房源同一时间仅允许一个 pending 变更审核单：编辑 A 类字段前校验，已存在则返回「已有变更待审核」
- 下架/上架/撤回/编辑均需校验房源归属（landlord）与当前状态合法性，避免状态机跳跃

### 6.3 兼容性
- 存量房源无 status 迁移需求（offline/change_reviewing 为新增值）
- 审核单模型复用，无需迁移
- 前端旧状态文案兜底（未知 status 展示原 code）

### 6.4 可扩展性
- 字段分级走 system_dict 配置，新增 A 类/免审字段只需改字典，不改代码
- 状态流转集中在工具函数，后续新增状态（如待下架）可扩展
